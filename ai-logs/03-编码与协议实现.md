# AI 对话记录 03 · 编码与协议实现

## 阶段
实现位打包、Huffman、三层协议，并修复相关缺陷。

## 人类指令（要点）
- 所有算法从零实现，不能只做“看起来像”；必须能编码也能解码，能自证正确。
- 位布局要能可视化，让非技术评委也看懂“为什么 5 个字节能救人”。

## AI 的实现
1. **位层**：MSB-first BitWriter/BitReader；LEB128 无符号 varint；定点坐标（纬 25 位、经 26 位）；工具方法 `alignToByte`。
2. **Huffman**：MinHeap 建树、码长统计、canonical 规范化；
   - 静态模型：对内置应急语料训练后作为 418 B 常量预装（UTF-8 字节全覆盖）；
   - 动态模型：完整实现表头随消息发送，徒步场景实测表头约 68 B，用于证明“短报文上动态不划算”。
3. **三层协议**：
   - L0 = tag2 + 类型2 + 粗纬16 + 粗经16 + 严重度2 = 38 位 = **5 B**（粗网格约 300 m × 500 m）；
   - L1 = tag2 + 时间戳31 + 纬差分9 + 经差分10 + 人数7 + 需求6 = 65 位 = **9 B**；
   - L2 = tag2 + 16 位短语标志 + varint 长度 + 静态 Huffman 文本。
4. **共享词典**：16 条双语应急短语，每条勾选只占 1 个标志位。
5. 对照项：JSON 基线、单体位打包、gzip（原生 CompressionStream）。

## 调试记录（真实发生）
- **缺陷**：动态 Huffman 解码补零后未对齐字节边界，导致后续解析错位。
- **修复**：为 BitReader 增加 `alignToByte()`，在 `decodeDynamic` 末尾调用；补充往返单元测试。
- **缺陷**：`mergeL1` 曾用解码出的粗坐标重新量化，产生误差。
- **修复**：直接使用 `decodeL0` 返回的整数粗网格 `latC/lonC` 合并差分。

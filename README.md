# 1% Battery

> 当手机只剩 1% 电量、只剩一条受损窄带，怎样让一条求救信息真正送达？  
> **Build for when almost nothing is left.**

北师港浸会 AI 赛道编程马拉松参赛作品（选题：**1% Battery**，工程与社会价值方向）。  
本作品是一个**纯静态、零依赖、可离线运行**的交互式教学/演示网页：它不假设网络与算力，而是把“在受限资源下完成任务”这件事做成了可点击、可实验、可复现的完整体验——所有算法从零实现，所有对比数字在你的设备上实时计算。

## 一、核心命题与资源约束

常规软件默认“资源充足”：带宽够、电量够、算力够、一直在线。但在灾后、徒步、偏远地区或旧设备上，这些假设同时失效。

本作品**显式声明并真实模拟**以下资源约束：

| 约束             | 取值（可调）                                                        | 说明                                                               |
| -------------- | ------------------------------------------------------------- | ---------------------------------------------------------------- |
| **极端窄带（主约束）**  | 带宽 100–2400 bps；单包丢包率 0–50%；停等往返 RTT 100–2500 ms；包载荷 16–128 B | 模拟灾后 2G 控制信道、受损链路；默认 600 bps / 丢包 30% / RTT 1.5 s / 32 B         |
| **能量预算（主约束）**  | 1% 电量 ≈ 410 J，可用滑块限定 5–410 J                                  | 3.8 V × 3000 mAh ≈ 41 kJ，1% ≈ 410 J；无线电 0.8 W、屏幕 0.4 W、CPU 0.3 W |
| **旧设备算力（次约束）** | 编解码耗时逐次测量并展示                                                  | 证明自研协议在旧手机上也是亚毫秒级                                                |
| **离线可用（次约束）**  | Service Worker 预缓存全部 19 个文件（约 146 KB）                         | 断网刷新依旧可用，零第三方请求                                                  |

任务不是“把数据压到最小”，而是**对信息排序**：让最能改变行动的信息（SOS、数百米区域、严重度）最先、最可靠地送达。

## 三、核心算法（全部从零实现，可解码往返）

1. **位打包**：MSB-first `BitWriter` / `BitReader`；LEB128 无符号变长整数；定点坐标（纬 25 位、经 26 位）；zigzag 等。
2. **三层分级协议**：
   - **L0 信标 = 5 字节**（tag 2 + 类型 2 + 粗纬 16 + 粗经 16 + 严重度 2 = 38 位）。粗网格约 300 m × 500 m，足以把救援队派往正确山谷。
   - **L1 定位 = 9 字节**（tag 2 + 时间戳 31 + 纬差分 9 + 经差分 10 + 人数 7 + 需求 6 = 65 位）。坐标以差分编码，必须与 L0 合并。
   - **L2 详情（变长）**（tag 2 + 16 位短语标志 + varint 长度 + 静态 Huffman 文本）。
3. **共享词典**：16 条中英双语应急短语（如“有人重伤，急需医疗救助”“请保持信号，不要关机”），勾选即只占 1 个标志位。
4. **静态 Huffman 模型**：由应急语料训练、规范化（canonical）后随 App 预装（模型 418 B，一次性成本、零流量分摊）。
5. **动态 Huffman 诚实对照**：完整实现“随消息发送表头”的动态方案（徒步场景表头约 68 B），真实呈现其在短报文上不划算的原因。
6. **gzip 对照**：使用浏览器/Node 原生 `CompressionStream`，展示通用压缩器在短报文上的局限。
7. **网络模拟器**：停等式 ARQ（每包尝试耗时 tx + RTT，期望 1/(1−loss) 次），固定种子 `mulberry32`，蒙特卡洛 300 次，结果可复现。
8. **能量模型**：`能量 = 无线电在线时间 × 0.8 W + 屏幕 × 0.4 W + CPU × 0.3 W`，系数透明、界面可调。

每次编码均通过 `roundTripOK` 做**编码→解码往返一致性校验**（20 项单元测试全部通过）。

## 四、对比数据（真实运行，可复现）

**A. 1000 条随机报文体积基准**（固定种子，`node tools/bench-node.mjs 1000`，Node v22.23.2）：

| 编码        | 平均字节       | 对比 JSON   |
| --------- | ---------- | --------- |
| JSON 整包   | 287.6 B    | 1.00×     |
| gzip（原生）  | 270.2 B    | 1.06×     |
| 单体位打包     | 83.9 B     | 3.43×     |
| **三层合计**  | **85.9 B** | **3.35×** |
| L1 定位（累计） | 9 B        | 31.9×     |
| **L0 信标** | **5 B**    | **57.5×** |

**B. 弱网送达表现**（600 bps / 丢包 30% / RTT 1.5 s，300 次蒙特卡洛）：

| 指标         | A · JSON 整包     | B · L0 信标       |
| ---------- | --------------- | --------------- |
| 平均送达时间     | 27.2 s          | 2.24 s          |
| p50 / p95  | 26.6 s / 35.9 s | 1.57 s / 4.70 s |
| 30 秒窗口成功率  | 71.3%           | 100%            |
| 无线电能量（不含屏） | 32.69 J         | 2.69 J          |

**首个可行动情报提速（TTFA）≈ 12.2 倍**；解析期望值（JSON 27.0 s / L0 2.24 s）与蒙特卡洛结果交叉吻合。

**C. 单次绝境终端（徒步场景，本次随机结果）**：JSON 270 B / 9 包 / 28.4 s / 34.1 J（超出 30 J 预算，零信息送达）；三层协议 L0 仅 5 B / 3.13 s / 3.76 J，完整 95 B / 21.1 s / 25.3 J（预算内送达）。

**D. 编解码耗时**：自研位打包/三层协议在 Node 上约 0.003–0.015 ms，浏览器约 0.02 ms（批量计时）；原生 gzip 约 0.3 ms（Node）/ 1.2 ms（浏览器）。全部为亚毫秒级，CPU 不是瓶颈。

- 页面上的**字节数、编解码耗时、网络模拟时间**均为当前设备真实计算，标注“实测”；可导出 JSON 复核。

- 开机自检中的真实电量、网络类型来自设备 API，仅作演示；“1% 电量”为作品设定的决策情境。
- 本作品未调用任何在线 AI 模型；AI 仅用于辅助开发，详见 [`AI_USAGE.md`](./AI_USAGE.md)。

## 九、设计原则

1. **优先级即设计（Priority is design）**：不是把所有东西变小，而是让最能改变行动的信息最先送达。
2. **为信息付费，而非为字节付费（Pay for information）**：重复字段名、固定字符宽度、可共享字典，都是不为信息增值的字节。
3. **优雅降级（Graceful degradation）**：L0 到了先派人，L1 到了精确定位，L2 到了了解伤情；残缺不等于无用。
4. **可度量才可信（Measure, then trust）**：每一个字节、毫秒、重传都可复现，不做无法验证的承诺。
